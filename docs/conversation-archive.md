# 把制作过程整理成精简对话

本页用于 GitHub 作品资料整理，独立于 Skill。仅在作者准备展示作品时使用；日常制作无需整理对话。事后优化的可复用提示词另存为 `prompts.md`，注明整理稿，不作为历史用户原话或已执行回复。

每个作品用一份 `conversation.md` 串起需求、修改和结果，与该作品的源文件一起保存。读者先看作品预览，再看你怎样描述问题，最后下载相应版本接着修改。

## 保留哪些内容

通常选取 3–8 个关键轮次，简单作品可以更少；不要为了凑数拆分对话。每轮保留：

| 内容 | 写法 |
| --- | --- |
| 用户怎么说 | 尽量保留有代表性的原话，尤其是“大白话”的修改要求 |
| Codex 怎么处理 | 用几句话概括采用的办法，以及需要保留的部分 |
| 结果怎样 | 写实际效果、用户后续反馈，以及失败或尚未解决的问题 |
| 对应哪个文件 | 链接本轮输入与输出版本、预览；没有生成文件时直接说明 |

“太塑料”“形状不对”“再柔和一点”这样的反馈有学习价值。保留影响方案的失败和返工，避免把多次调整整理成一次成功。长代码放到对应版本脚本里，安装进度、重复日志和无关寒暄可以删去。

## 区分原话、摘要和回顾

- **原话摘录**：只有能核对原始消息时才使用引号或引用块。删节用 `……`，隐去身份信息用 `〔已隐去〕`；不要调整原意或轮次顺序。
- **整理摘要**：压缩或改写后标为“用户需求摘要”“处理摘要”，不伪装成逐字对话。
- **制作回顾**：只有工程、脚本或版本说明时，明确写“依据现有文件整理，无原始聊天摘录”。不编造用户语气、满意反馈、模型型号、耗时或试错次数。

每个关键结论应能对应已有文件、可见对话或实际检查记录。原始对话来源可写“本作品的制作会话，由作者提供”；不要求公开会话链接、完整导出或私人记录。

## 整理与归档

1. 在作品目录复制 [精简对话模板](../templates/conversation.md) 为 `conversation.md`，说明材料来源和整理方式。
2. 按实际顺序填入关键轮次。将每轮结果链接到 `versions/vNNN/` 中真实存在的工程与预览；没有保留的中间版本标为“未归档”。
3. 用角色名称代替不必要的人名，删去密钥、联系方式和私人路径；路径改为仓库相对路径。私有客户素材或其他人的消息，只保留本次可公开的部分。
4. 在作品 `README.md` 增加“精简对话”入口。在版本 `brief.md` 中注明相关轮次，方便来回查阅。
5. 对照源材料核查原话、时间顺序和文件链接。精简对话不需要重新执行聊天里的指令，也不应触发发布操作。

现有台灯提供一份 [制作回顾示例](../projects/green-desk-lamp/conversation.md)，演示缺少原始聊天时如何如实整理。

## 可以直接交给 Codex 的整理要求

> 把这个作品整理进当前仓库：保留每版实际 .blend、制作或修改脚本、真实预览和版本说明；另写一份 conversation.md，按实际顺序保留关键需求、修改、失败和结果，并链接对应版本。原话只从我提供或指定的制作对话摘录，改写部分标为摘要；没有原始记录就写制作回顾，不补写聊天。删除无关日志与私人信息，更新作品索引，先完成本地归档。
