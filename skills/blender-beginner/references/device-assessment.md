# 设备与渲染适配评估

用户关心「电脑带不带得动」「适不适合 4K」「动画要多久」时读取。需要的是针对目标场景的实测建议，不能按品牌或单个硬件型号给万能性能分。评分与参考图可实现度分开记录，再作为其设备预算维度的证据。

## 先分开三个判断

1. **运行兼容性**：Blender 版本能否启动，所需渲染引擎/设备后端能否工作。
2. **容量与稳定性**：目标场景是否在内存、显存或统一内存、缓存与输出空间内，目标设置下能否完成。
3. **时间是否可接受**：单帧、整段动画、模拟烘焙分别耗时多少，是否满足用户可等待时间。

GPU 可用、简单小图成功和复杂 4K 场景可交付是不同证据。4K 默认指 UHD 3840 × 2160；用户要求 DCI 4096 × 2160 或不同画幅时按实际尺寸计算。高分辨率本身不保证材质细节、采样质量或画面美观。

## 第一步：只读检测

先确认目标设备是否是当前执行主机。用户讨论另一台电脑时，使用那台电脑的检测报告或明确标记的用户提供信息；不要用当前主机的实测去给远端 Mac 下结论。没有目标设备访问能力时保留未知，提供在目标设备上最少需要读取的项目。

复用同一机器、Blender 版本、实际后端和适用场景设置的已有记录；仅在目标变化、成本明显增加或出现失败时补测相关项。空闲空间和可用内存是时点快照，接近容量上限或开始昂贵工作时应刷新相关值。普通参考图咨询或术语翻译无需为了填全评分而执行检测。

运行 [硬件探测脚本](../scripts/inspect_hardware.py)，由系统 Python 3.10+ 执行：

```text
python inspect_hardware.py --output <新建的硬件报告绝对路径.json>
```

收集 OS、CPU/芯片、RAM、GPU/驱动、可靠来源的显存、输出盘可用空间；不要扫描用户文件或列出进程私人内容。无法读取的值标为未知，不填 0。显存只有不可靠 Windows AdapterRAM 数据时不作容量依据。

Mac 另外识别 Intel / Apple Silicon、是否通过 Rosetta 运行、统一内存和电源模式。Apple Silicon 的统一内存是 CPU/GPU 共享资源，不能写成同容量独立显存，也不能把总量当作本次可用量。[Apple 统一内存说明](https://developer.apple.com/documentation/metal/choosing-a-resource-storage-mode-for-apple-gpus)

GPU 名称不证明已经启用加速：实际核对 Cycles 的后端、设备开关和场景设备。Metal 支持随 Blender、macOS、芯片变化，按当前版本官方文档与运行结果判断；不能把旧版 Intel Mac 的兼容性套到新版。当前 5.2 文档中的 Metal GPU 路径面向 Apple Silicon。[Blender GPU 渲染](https://docs.blender.org/manual/id/5.2/render/cycles/gpu_rendering.html)

电源和持续负载条件也要记下；不要自动修改系统电源设置。探测脚本记录供电方式，尚不检测低/高电源模式、温度或降频；需要进一步诊断时另读可用设置。Mac 能源模式适用机型不同，读到什么记什么。[Apple 能源模式](https://support.apple.com/en-ie/101613)

## 第二步：限时试渲染

用户只是讨论技能设计时不在其电脑上进行性能测试。用户要求评测当前设备或实际制作时，短时诊断属于该工作的一部分；先说明测试目标、场景和限时，不重复索取已经有的授权。

优先使用目标工程的副本或只读加载目标工程。尚无工程时可以用起步模板产生简单小样，但结果必须标为「基础场景」，不能迁移为复杂角色/室内/流体的性能承诺。没有 Blender 时仅给静态检测，不伪造实测。

使用 [限时调用器](../scripts/run_benchmark.py) 启动独立后台进程，它调用 [单帧探测](../scripts/benchmark_frame.py)：

```text
python run_benchmark.py --blender <Blender可执行文件> --blend <已有工程.blend> --output-dir <全新绝对目录> --width 960 --height 540 --samples 16 --backend AUTO --timeout 90
```

上例 960 × 540 是 16:9 示例值；调用前沿用目标或原工程的宽高比缩小尺寸，通常从 16 采样、最多 90 秒试起。每次只测一帧，独立目录保留预览、设置、设备和耗时。`AUTO` 选择本机枚举到的可用后端；成功渲染才算实际验证。明确指定的 GPU 不可用时报告失败，不偷换成 CPU。检测合成器文件输出节点、多视图或活动视频序列时，探测会拒绝渲染；按用途另准备受控副本后再测，不静默丢掉用户需要的效果。

调用器超时会终止它启动的 Blender 进程。超时、崩溃、显存不足要如实区分；一次超时不等于硬件永远不支持。不要接着无界限轮测所有后端，也不要自动开始整段 4K 动画。

报告里的时间是一次渲染调用的总耗时，可能包括依赖图、内核编译、去噪、合成和写图。启动器另记进程总耗时。它不是官方 Blender Benchmark 分数，也没有测到峰值内存；硬件空闲内存快照不能替代峰值测量。

测试尺寸改变画幅时，原相机的构图可能裁切主体。脚本不改变相机或保存工程，性能通过也不表示画面构图合格；比较两次耗时要记录画幅变化，并在正式成片前重做构图检查。

## 第三步：逐级验证目标与预算

小样通过后，结合用户目标决定下一次检查，而非默认运行所有组合：

- 要 4K 静帧：先判断小样表现与内存风险，再在独立进程中检查一张完整 3840 × 2160 的代表帧。低采样成功只验证该采样与功能设置；最终采样、去噪或通道增加后需重新评估。
- 要动画：在目标/接近目标的设置下检查开始、中间、结束和明显最重的帧。若要判定长期速度，需在获准预算内观察连续帧；单次小图无法证明散热稳定性。
- 有流体、布料、毛发、体积、几何节点或运动模糊：分别检查缓存/模拟与渲染成本，镜头走向可能改变最重帧。
- 给出建议时同时写「已验证设置」「尚未验证设置」和下一步最低成本的验证，避免绿色标签掩盖未知。

## 耗时估计的边界

在相同场景、引擎、后端、功能和近似采样工作量下，可用以下式子做**工作量推算**：

```text
目标采样工作量比例 ≈ (目标宽 × 目标高) / (测试宽 × 测试高)
                   × 目标采样数 / 测试采样数
动画帧数 = 已明确的时长 × fps（已有时间线则用实际帧数）
```

1080p 到 UHD 4K 的像素数是 4 倍，不能由此断言一定慢 4 倍。内存溢出、去噪、合成、自适应采样、首次编译与模拟使耗时非线性。不能直接把「冷启动总耗时 × 像素比 × 采样比」伪装成可靠 ETA。

有多个代表帧实测时，给出其单帧耗时范围与整体粗估，注明依据：粗估总渲染时间约为单帧范围 × 待渲染帧数，再列出尚未计入的烘焙、重试、合成、编码与持续降速。样本范围不保证覆盖全片；数据不足就写待测，不凭型号编造分钟数。

用户给出截止时间时，明确该时间覆盖制作、模拟烘焙、渲染还是全部交付。可先反算每帧预算：可用于渲染的秒数 / 帧数。比如 20 分钟完成 30 秒、30 fps 的 900 帧，即使全部时间用于渲染，也需平均不超过 1.33 秒/帧；这是期限要求，不是设备实测速度。

算术教学例：若同设置的代表帧实际在 10–20 秒之间，10 秒、30 fps 的动画为 300 帧，纯帧渲染粗估约 50–100 分钟。这里的秒数是假设，不是任何电脑的性能结论。

单帧输出大小 × 帧数可粗估帧序列空间，EXR 通道、压缩和复杂度会改变大小；模拟缓存单列。编码器能输出 4K 视频不证明 Blender 能按目标速度渲染 4K 场景。

## 给新手的设备适配卡

```text
设备：具体芯片/CPU、GPU、RAM或统一内存；未知项写明
目标：3840×2160静帧 / 动画时长、fps与画质；允许等待多久
加速状态：实际验证的后端 / 仅发现设备 / 未验证
预览：已实测的场景、尺寸、采样、单帧耗时
4K静帧：已验证 / 可尝试、待验证 / 先简化 / 当前阻塞
动画：已测代表帧与估计 / 待测；不能用静帧结论代替
主要限制：内存、显存、统一内存压力、时间、缓存或兼容性
建议：保留什么效果，降低哪些成本；列明与参考的差异
把握程度与下一步：……
```

降成本优先按用户重视程度选择：先用小图预览、去掉不影响画面的几何、降低不必要的细分与贴图尺寸，再试合理采样/降噪；EEVEE 与 Cycles 的材质/光照可能不同，换引擎需比较画面。不能静默降低成片尺寸、帧率或关键视觉。云渲染属于用户选择的后续方案，不自动上传文件或产生费用。

## 已验证范围

硬件探测与限时调用器提供 Windows/macOS 路径；Windows 在当前机器实测，macOS/Metal 路径仍需真机验证。已有 Windows 安装器的支持范围保持不变，设备评估扩展不等于已经实现 Mac 自动安装。
