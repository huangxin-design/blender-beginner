# Blender 新手开工助手

按本次请求选择咨询、评估、新建或继续修改，复用已有环境、工程和适用证据。用用户使用的语言交流；由 Codex 处理安装、Python、路径和节点接口，新手只需描述结果和看预览。用户要求确定目标，实际证据确定可行性与完成状态；默认值只填未指定部分。

## 按用户目的选择流程

| 用户当前想做什么 | 应完成什么 |
| --- | --- |
| 安装、配置、把工作文件放到指定盘 | 环境准备卡、安装配置、独立验证和打开方法 |
| “我的电脑/Mac 能不能做 4K 或动画，为什么很慢” | 硬件记录、有限时的目标场景试渲染、设备适配卡与预算依据 |
| 贴图问“能不能做、能还原多少” | 参考图评估卡、可实现度和依据、限制与可选简化方案 |
| “帮我把这段描述变成 Blender 提示词” | 保留原话的制作任务书，说明节点、参数方向和验收条件 |
| “按这张图/描述帮我做出来” | 必要的前期检查，再生成、重开、渲染和交付 |
| “刚才那版太塑料/改颜色，其他不变” | 读取当前指定工程，诊断相关差异，局部修订、另存与复核 |
| “这个项目用了多少 Token” | 明确记录区间与来源，展示已记录用量、截至时间、待结算和未覆盖部分 |
| “渲染还要多久，给我看看进度” | 本次受控渲染的阶段、已用时间、完成帧数与有依据的剩余时间范围 |

只做参考评估或文字翻译时，到相应结果为止，不为补齐分数而检测本机、安装或渲染。用户要求评测本机时可做有关的限时诊断。已明确要求安装或制作时继续执行，不把每个中间步骤变成待批准事项。没有参考图时评分待评估，可继续已请求的文字分析；缺图本身不触发环境准备。

多步制作、跨轮修改或目标冲突时读取 [项目衔接与反馈](references/project-loop.md)：复用一份任务记录，保留必要要求、已采用路线、最近成功版本与下一步。在选路线或出现新证据时检查最可能失败的条件，只整合相关修正；简单任务不增加整套评审。阻塞要指出具体哪项要求未满足，已授权且不依赖该条件的可逆工作继续。

## 1. 准备 Blender 与工作目录

需要安装或配置时读取 [环境准备](references/onboarding.md)。先查已有环境，沿用用户指定的 D/E 盘或其他路径。新安装用独立目录，并把配置、项目、渲染和可控制的临时文件一起安排好。

[Windows 安装器](scripts/install_blender_windows.ps1) 提供只读准备卡和真正安装两条路径；[配置脚本](scripts/configure_blender.py) 负责中文、自动保存、初始场景和实际渲染验证。当前自动安装支持 Windows x64 / Blender 5.2 系列，其他系统版本不冒充已适配。

只讨论产品方案时不下载安装。已有可用 Blender 优先复用；不把“放在 D 盘等位置”的举例当作迁移当前安装的命令。不修改既有偏好，除非用户要求；新的隔离安装按已授权的设置需求配置。

## 2. 判断设备与渲染目标是否匹配

需要设备判断时读取 [设备适配评估](references/device-assessment.md)。先确认待评估设备是否就是当前执行主机；讨论另一台 Mac 时不能套用当前 Windows 的数据，应使用目标设备报告并标注来源。复用同一目标设备、版本、后端及适用场景设置的已有证据；目标改变、成本明显增加或出现失败时才补测相关项。需要补测时用 [只读硬件探测](scripts/inspect_hardware.py) 和 [限时单帧试渲染](scripts/run_benchmark.py)，不为一次局部改色重跑全部设备测试。

分别判断运行兼容、场景容量与可接受耗时，给出预览、4K 静帧、动画的独立结论。简单小图成功不证明复杂 4K 或整段动画可交付；没有工程时仅能做基础诊断。读取参考图任务的设备预算维度时引用这些证据，不再凭机器型号猜分。

Mac 单独核对 Intel/Apple Silicon、实际 Metal 渲染和统一内存；不能说所有 Mac 都慢，不能把统一内存当独立显存。未知温度、降频、峰值内存或长期性能应标明未测。动画先看代表帧与最重场景，再按帧数粗估；不要直接把冷启动小图时间线性放大成精确 ETA。

## 3. 评估参考图

用户要可行性评估，或制作前有影响路线的新难点时，先实际查看参考，再按 [参考图评估](references/reference-assessment.md) 判断。继续修改只更新受影响的判断，不因附带参考图而重做全卡。默认评估固定视角静帧与可编辑工程，明确假设；自由旋转模型、动画或打印要按用途另评。

分别说明几何、材质、灯光镜头、素材、设备预算这五项的证据，形成 0–100 的方案评估分；同时给置信度、预计不同之处和最先验证的难点。分数不是成功概率或还原百分比。信息未齐时给待评估或范围；不可替代条件缺失要突出阻塞，不能被平均分掩盖。

## 4. 把大白话变成可执行制作需求

读取 [语言到 Blender 的翻译规则](references/language-to-blender.md)。原话、视觉目标、技术选择、可调整参数方向、暂定假设、验收方法应互相对应。先给用户一小段易懂的目标描述，再保留供 Codex 执行的详细任务书。

Blender 本身不理解自然语言提示词；任务书由 Codex 转成实际节点、对象、相机、灯光和 `bpy` 操作。不能只把“有肌理、梦幻、高级”替换成英文术语。尤其区分颜色混合/属性混合/Mix Shader/Coat、凹凸贴图/真实几何、发光材质/照明/画面光晕、景深/普通模糊。

## 5. 用户要求制作时整理场景

先用一两句话说明主体、风格、用途、交付内容和必要假设。尽量沿用已有信息；只询问会明显改变结果的缺项，例如究竟是静态摆件还是要用于动画的角色。不要让新手选择 Python 接口或渲染参数。

- 新场景没有其它规格时：单个静态场景、公制单位、材质和光照齐全，约 960 × 720 预览。已有用途或工程则继承其单位、画幅和关键设置，小样等比例缩小；改变画幅时重新检查构图。
- 有参考图时：先查看原图，提取轮廓、比例、材质与视角。单张图片中看不到的部分属于建模假设，不声称精确重建。
- 大场景先做布局与主要体块再补细节；已有工程先读取结构，再按对象名称修改。
- 输出位置使用当前用户项目中的独立版本目录，例如 `outputs/desk-lamp/v001/`。不要把生成结果写回技能资源目录。

### 检查执行环境

按 [执行与排错](references/runtime.md) 找到 Blender 可执行文件并读取实际版本。普通生成与复核用 [限时执行器](scripts/run_blender.py) 记录本次时间预算、退出状态和日志；超时保留最近成功版本。`bpy` 脚本由 Blender 自带的 Python 运行，不要求用户在系统 Python 中安装 `bpy`。只承诺实际验证过的版本。

默认使用独立的 Blender 后台进程。只在需要操作用户正在打开的场景、且已提供可调用连接时使用 MCP。实时会话先读取当前场景和保存状态；需要原地修改或覆盖前核对既有授权。不要把“制作一个文件”扩大为安装 MCP、开启网络服务或更改全局偏好。

找不到 Blender 时，仍可完成脚本与执行说明，但明确 `.blend` 和渲染尚未生成。先给出检测结论和最少的下一步；不要编造文件或成功记录。

### 生成可编辑工程

新建小型产品场景可以复制 [台灯起步模板](assets/starter_scene.py) 到项目的版本目录，再按用户需求改写建模部分。它用于展示最小制作流程，不限制用户的主题，也不是通用建模器。

- 对象按用途命名，例如 `Lamp_Base`、`Lamp_Shade`、`Camera_Main`；几何、布景、灯光、相机分组，保留有意义的独立部件和修改器。
- 设定尺寸、材质节点、相机和场景照明。根据场景选择 EEVEE 或 Cycles；先以适当分辨率检查，用户需要高质量时再提高渲染成本。
- 后台脚本避免依赖界面区域、鼠标选择或手动切换模式；优先直接访问数据，使用操作器时明确对象及上下文。
- 新建脚本可以清空其独立进程中的初始场景；修改用户的已有工程时不要套用清空场景模板。
- 使用外部纹理、模型、字体时记录来源和使用条件，打包可打包的资源，并检查重新打开后的依赖。缓存、序列等资源必要时随工程交付。
- 存入全新 `.blend` 路径。保留生成或修改脚本供复现；修改时递增版本，避免覆盖唯一原件。

### 重新打开、渲染、查看

生成脚本返回成功还不算验收。启动另一个 Blender 进程打开已保存的 `.blend`，用 [检查脚本](scripts/inspect_scene.py) 写出结构报告并渲染预览。精确调用方式见 [执行与排错](references/runtime.md)。

然后实际查看预览：主体是否完整入镜，是否出现黑图、粉色缺失纹理、明显穿插、漂浮、比例或材质问题。结合原始需求评价，而不只看文件是否存在。按 [项目衔接与反馈](references/project-loop.md) 对照主要差异；先处理轮廓构图，再完善材质光照，提高采样不能替代纠正方向。检查器只覆盖基础静态场景；它的成功不代表视觉质量、拓扑、3D 打印或复杂动画已经合格。

有明确问题就修改并重新验证相应结果。失败时根据日志修复具体原因；相同失败重复发生且没有新线索时，保留诊断并说明阻塞点，避免无限重试。无法查看预览时标记视觉检查未完成。

动画任务另查时间范围、关键帧、缓存，并至少检查开头、中间、结尾；交付前按 [验收场景](references/acceptance.md) 选择有关检查。不要为静态任务创建动画或其他额外交付。

### 给新手交付

交付可点击的 `.blend` 路径、真实预览图，以及简短的已检查项目与尚存限制。版本目录中保留生成脚本、检查报告和必要日志；用户只看主要文件即可。

补充最少使用提示：在 Blender 中打开工程，按数字键盘 `0` 看相机，`F12` 渲染；也可直接继续用自然语言要求修改。不要要求用户复制长脚本到 Blender 才算完成。

## 6. 记录项目用量

用户需要用量统计时读取 [项目 Token 记录](references/token-usage.md)。在明确的单项目、单会话来源上建立基线，工作节点更新记录，结束时请求关闭；尚未收到对应回合结束事件时保持待结算。没有来源的旧 `.blend` 显示“未记录”，不能凭文件大小、精简对话或运行时长补算。

用量标题写“项目已记录用量”，同时显示记录范围、实际用量截至时间及覆盖限制。输入缓存和推理输出分别属于输入和输出的子项，不重复相加。混合项目、子代理和分叉继承不能自动准确归属；不得换算为账户额度或虚构费用。记录只在本地保存，作品归档与公开仓库不默认收集会话、账本或本机路径。无需为不要求统计的咨询追查用户历史会话。

## 7. 显示渲染进度与预计剩余时间

需要进度时读取 [渲染进度](references/render-progress.md)。用限时执行器的 `--progress` 启动本次任务；普通脚本只提供已能识别的阶段与采样信息，需要整段帧计数时采用受控 PNG 帧输出脚本并给出明确帧列表。此功能不监听用户已在界面中启动的任意渲染，也不把视频编码或验收计入帧输出 ETA。

先显示阶段、已用时间和数据更新时间，首帧单列。至少获得三个后续完整帧后才给低可信经验范围；复杂度变化、超出历史范围或进度过期时撤回估计并说明原因。预计时间可以增加；采样剩余为零不能显示任务完成。失败、超时和中断必须结束本次状态记录并保留日志。

提供本地 `progress.html` 让用户查看；它由执行器更新，不需要常驻服务，也不需要每秒调用模型。结束后分别说明执行结果、输出检查和视觉验收；PNG 存在性检查不替代实际查看，视频另按项目要求检查软件／硬件解码与目标播放器。

## 扩展边界

本技能首先服务制作前的环境、设备适配、参考图评估与翻译；实际制作沿用本地脚本与文件交付，不依赖特定 OpenAI 模型名称。只有用户问最新模型或能力时才重新核验官方来源。后续按真实需求增加角色、室内、动画或实时 MCP 专项参考，不预先堆叠框架。
